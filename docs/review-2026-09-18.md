# Revue de la configuration et du packaging

Revue du 18 septembre 2026, base Git `6afffc8`, puis corrections locales.
Périmètre : `init.lua`, lockfile, trois scripts de déploiement, README et
documentation Java. Les outils personnels et plugins actifs n'ont pas été
réinstallés ; les installations de test utilisent des HOME temporaires.

Le runtime du wrapper est désormais épinglé à Neovim v0.12.5, le CLI à
Tree-sitter v0.26.1. Les fallbacks npm/pip de l'installation ont été retirés
en faveur de Bun/uv. `init.lua` a été formaté avec le `stylua.toml` existant.

La validation Docker a ensuite reproduit un **P1 supplémentaire** : le build
annonçait 23 parsers alors que CSS manquait (le parser `dtd` masquait ce manque
dans le comptage). L'installation automatique, le hook `:TSUpdate` et les
appels headless interrompus ou concurrents produisaient des erreurs
`Could not rename temp: ENOTEMPTY`. Désormais, sans UI attachée, ni le hook ni
la configuration ne lancent la compilation. Le wrapper lance une installation,
l'attend, puis contrôle les parsers dans un nouveau processus Neovim avant
d'exporter. Le test d'acceptation a échoué sur l'ancienne archive et passe sur
l'archive corrigée. L'installation automatique reste active en TUI normal.

## Points ouverts de la configuration

1. **P2 — rechargement non fiable** (`init.lua`, mapping `<leader><CR>`).
   Un deuxième `:source` affiche `Re-sourcing your config is not supported with
lazy.nvim` et fait passer le nombre d'autocmds de 363 à 375 dans le test
   isolé. Redémarrer Neovim ; ne pas présenter ce mapping comme un reload complet.
2. **P2 — isolation des workspaces Java** : ils utilisent le nom du projet
   sans hash du chemin. Deux projets homonymes peuvent donc partager l'état
   jdtls. Le commentaire `ponytail:` identifie déjà cette limite.
3. **P2 — détection Java** : le marqueur le plus proche est retenu, sans
   remontée au réacteur Maven ni marqueurs `settings.gradle.kts` /
   `build.gradle.kts`. La spec historique décrit des travaux encore partiels.
   Pas de certification des projets Ant/Maven multi-modules/Gradle pendant
   cette revue : il faut les fixtures et des projets représentatifs.
4. **P3 — diagnostics de maintenance masqués** : `vim.deprecate = function()
end` supprime globalement les avertissements de dépréciation. À retirer
   lors d'un lot de maintenance des APIs, avec validation des plugins.
5. **P3 — vérification online partielle** : `--check` contrôle les binaires
   listés, pas le fonctionnement de chaque serveur. `lua-language-server` et
   `goimports` restent à provisionner séparément. Bun et Node sont désormais
   contrôlés séparément, pour l'installation et les lanceurs des outils JS.

## Limites du packaging

- OS et CPU ne suffisent pas à certifier une ABI Linux. Le runtime officiel
  testé est incompatible avec OL8 ; l'archive corrigée passe sur UBI 9.6.
  Ce résultat ne couvre pas tous les hôtes RHEL9 ni les futures archives. Voir
  l'[étude Enterprise Linux](packaging-enterprise-linux.md), avec sources.
- L'export contrôle les sources des plugins, pas la provenance des fichiers
  non suivis, du binaire blink ou des parsers. Il faut `:TSUpdate` après un
  changement de commit Treesitter et une réception sur la cible.
- Un bundle sans parsers ou Java reste exportable avec avertissements. Les
  LSP, formatters, JDK et outils de recherche/Git ne sont pas embarqués.
- L'image Docker, jdtls et les extensions VS Code ne sont pas entièrement
  verrouillés ; il manque un manifeste de provenance et des checksums pour
  un build reproductible. Les sauvegardes de l'offline sont conservées, mais
  son déploiement complet n'est pas transactionnel et le runtime embarqué
  est remplacé séparément.
- Les scripts supposent les chemins HOME standards. Les réglages XDG ou
  `NVIM_APPNAME` personnalisés demanderaient une prise en charge explicite.

## Preuves d'exécution

- `bash scripts/test-packaging.sh` : 13 scénarios passent, après reproduction
  des échecs avant correction. Faux binaires, vrais exports/installations dans
  des HOME temporaires, aucun réseau.
- `shellcheck scripts/*.sh`, syntaxe Bash des scripts et de l'installeur généré,
  `stylua --check init.lua`, `git diff --check` : contrôles locaux exécutés.
- `scripts/install.sh --check` : Neovim 0.12.0-dev, Tree-sitter 0.26.12,
  Bun 1.3.10 et les 10 outils contrôlés présents. `--dry-run` exécuté également.
- Test natif isolé : copie temporaire des 22 plugins, checkout des commits
  verrouillés dans ces copies uniquement, export puis installation sous
  `unshare -Urn` (réseau coupé). Neovim headless charge les **23 parsers**,
  compile leurs queries de highlights, parse un buffer et démarre le
  highlighter pour chacun ; le moteur fuzzy **Rust** de blink est chargé.
  Sortie : `PASS native smoke: 23 parsers + highlight queries + Rust fuzzy`.

- Docker 29.0.1 désormais disponible : build Fedora 43 réussi, **24 parsers
  compilés** (23 configurés + `dtd`, dépendance XML). Le contrôle pré-export
  `scripts/check-runtime.lua` charge effectivement chaque parser et query.
- `bash scripts/test-offline-linux.sh` : **succès Fedora 43** ; même commande
  avec `registry.access.redhat.com/ubi9/ubi:9.6` : **succès UBI 9.6**. UID/GID
  10001, réseau coupé, système de fichiers en lecture seule, HOME temporaire.
  Le runtime testé est cette fois le Neovim v0.12.5 embarqué dans l'archive.
- Même test sur `oraclelinux:8` : **échec attendu**, runtime refusé. Le probe
  direct du binaire identifie les symboles GLIBC_2.29/2.32/2.33/2.34 manquants.
- Archive et checksum sous `dist/` ; traces sous `logs/docker-build-*` et
  `logs/docker-test-*`. Digests et checksum dans l'étude Enterprise Linux.

**Non vérifié** : runtime compilé pour EL8, hôte RHEL abonné, macOS, arm64,
intégration graphique, clipboard WSL, LSP/DAP/tests Java de bout en bout.
Les images de réception n'ont pas Git : gitsigns le signale ; les fonctions
Git demandent toujours ce binaire externe. Un TUI Neovim minimal a confirmé
qu'une UI est attachée, sans constituer un test visuel complet de la config.


## Suite du 19 septembre : build OL8

Le runtime 0.12.5 est maintenant compilé avec les outils OL8 standards.
La recette `export-offline-el8.sh` ajoute un JDK 25 réservé au serveur jdtls,
Node, Pyright et Ruff. Les JDK des projets Java restent indépendants ; les
variables de runtimes couvrent les versions 8 à 25. Voir le
[guide OL8 Java/Python](offline-el8.md) pour la réception et ses limites.

Deux défauts supplémentaires ont été reproduits puis corrigés : la sauvegarde
du runtime et du lanceur avant remplacement, et les diagnostics pull de
Pyright 1.1.411 qui pouvaient disparaître après des refresh concurrents sous
Neovim 0.12.5. Le mode push natif de Pyright est utilisé. Le snapshot jdtls
1.62 dépendait déjà de Java 25 via Eclipse ; le packaging épingle désormais
la release 1.61.0 et utilise un JDK 25 explicite.


Réception finale du 19 septembre : **OL8.10 et UBI 9.6 passent** le socle
natif, Pyright/Ruff et la matrice des projets Java 8/11/17/21/25 avec serveur
JDK 25. ShellCheck, StyLua et les 14 fixtures de packaging passent. Le checksum
et les limites de validation sont consignés dans l'étude Enterprise Linux.
